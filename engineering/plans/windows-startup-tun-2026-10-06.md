# Windows 启动时自动开启代理与 TUN

状态：用户已明确要求修复，执行中。基线 `development@d2708be491c8002400a657b66bde93eda6a16ce3`。本需求修订前一批“应用启动只读接管”的产品行为；前一批测试与包仍按原来源保留，不回写成新行为已验收。

## 需求与范围

1. 有有效配置时，每次完整启动 Windows 应用自动完成代理与 TUN 启动，不再要求先点代理再点虚拟网卡，也不受历史 `autoRun=false` / `tun.enable=false` 阻断。
2. 已匹配的后台代理与 TUN 真实运行时只接管，避免重新应用配置、重复启动 listener 或授权。此时本地没有 profile 不应破坏后台运行。
3. 检查配置、组件合同与身份后，按需申请一次权限；初始化 Core/state、应用完整配置、启动 listener，再从真实观测确定是否开启。单纯保存意图不等于成功。
4. 缺少配置、解析失败、组件不匹配、权限拒绝、初始化/配置/listener 失败均明确报告；失败后的显式重试仍是完整流程。
5. 自动启动每个应用实例只执行一次。本次会话手动关闭后，resume、重连、轮询、provider 更新不会擅自再开启或触发 UAC；退出、取消和较新的关闭意图使旧异步结果失效。
6. 保留非 Windows 启动行为。`autoLaunch` 控制 Windows 登录时是否运行应用，与运行应用后的自动启动代理不同。保留购买页面全部入口。

非目标：改变 Mihomo 固定版本、协议/栈、路由规则、服务安装策略、WFP/驱动、其他平台默认值、在线支付；不承诺特定 IDE 流量已修好。本轮无远端推送、PR、主线合并或部署。

## 根因与方案

上一批 Windows `_initStatus` 只读投影 Agent 状态，而 `setTunEnabled` 在代理未运行时不完成完整 profile/listener 启动。只改布尔默认值不能修复入口。

在生产初始化链加入一次性完整启动事务，与现有 TUN 意图、串行队列和真实状态观测共用控制器。事务内部使用不再入队的底层步骤，避免等待自己造成死锁。外部边界以最小注入提供受控集成测试，生产仍调用原服务、权限与配置实现。配置读取、授权和其他长异步边界检查当前意图，避免取消后的迟到写入。重连本身仍只读，不被用作新的启动入口。

迁移取消边界：发送旧后台 shutdown 之前必须确认当前意图；旧后台实际退出已确认后，后端交接进入有界的最低恢复段，允许完成新 Core 连接与必要初始化，以便排队的关闭/退出仍能控制明确归属的后台。取消后的旧开启事务禁止继续配置 TUN 或启动 listener；未确认旧进程退出不得启动新实例。这里不能把“取消开启”描述成能够撤回已提交的后端交接。
