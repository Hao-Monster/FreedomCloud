## 2. 方案选择

### 推荐：购买页统一体验，加购买专用安全接口

仅在客户端购买页增加结算交互；在 Xboard-Go 增加必要的账户购买上下文、报价、确认/恢复接口和防重复执行记录。复用现有金额、套餐资格、兑换限制、订单、权益及审计规则；旧路由和其他页面行为保持兼容。

主流程：

浏览套餐 → 选择套餐/周期 → 必要时在购买页登录 → 选择余额或兑换码 → 服务端核验与报价 → 用户明确确认 → 执行并确认订单 → 同步订阅。

余额型码的“核销入账、标准订单余额扣款、订单完成与权益发放”建议在一个数据库事务中完成。余额不足、价格/权益变化或业务失败时全部不生效，不留下“卡已消耗但套餐未购买”的中间结果。请求成功但响应丢失时通过同一个请求编号找回结果。

这是一项待确认的新购买接口行为，不改变旧通用卡单独兑换的充值语义。外部发卡网的现金收款、第三方付款和本机订阅文件同步不在这个数据库事务内。

### 不推荐作为最终形态：只用旧接口串接

可以做分阶段预览：先充值、再创建会预占余额的订单、再确认完成；必须接受充值与购买不原子、缺余额读、价格变化后暂停、创建结果不明时人工核对等限制。不能承诺“用户确认金额之外绝不预占”或无交互精确恢复。该方案不是推荐方案的等价替代，不擅自以降级体验交付“完整购买”。

这一路径也不能把充值插在创建订单之后：旧checkout不会重新使用新到账余额。已有待付款订单必须先展示并由用户显式处理，不能自动取消和重建。

## 3. 推荐业务规则（待随基线确认）

| 决策 | 推荐规则 |
| --- | --- |
| 付款方式 | 账户余额；兑换码。没有真实通道时不展示虚假的微信/支付宝在线支付选项 |
| 余额型兑换码 | type1且本次实际奖励只有正余额；遵守全部原模板限制，不在客户端放宽 |
| 余额组合 | 可以用账户已有余额加一个余额型码结算；余额已足可不输入码；超出部分留账户，确认页提前写明 |
| 不足金额 | 不核销、不扣款、不创建未完成订单；明确差额，保留选中套餐并提供购卡/客服入口 |
| 多码与混付 | 首版不新增一笔交易多码合并、现金补差、自动充值或自动续费；原有独立兑换入口仍可使用 |
| 指定套餐码 | type4仅用于卡快照匹配的套餐/周期；展示真实权益变化，保留同套餐叠加/续期及不匹配拒绝，不替换标准订单规则 |
| 其他礼品卡 | type2/type3和混合奖励type1仍走购买页原有兑换功能，不伪装成现金付款 |
| 新购/续费/换套餐 | 复用后台已有资格与结算规则；任何可能替换额度、清零已用、改变到期日的影响必须在确认前显示 |
| 价格与币种 | 由服务端提供币种、整数最小单位、优惠/折抵/余额使用和最终应付；不猜货币符号，不自行复制结算公式 |
| 价格或权益变化 | 确认时重新校验；与已确认报价不一致则无消费拒绝，重新报价并再次确认 |
| 现有订单 | 显示当前未完成订单并由用户明确处理；不自动取消或支付网页/另一设备创建的订单 |
| 成功判断 | 仅服务端确认订单已完成/指定套餐码已成功才显示购买成功；同步失败单独展示并仅重试同步 |
| 重复与恢复 | 同一请求键同一交易意图最多执行一次；超时保留待确认状态，不生成新键重试、不靠列表顺序猜结果 |

不自动创建/修改线上余额卡模板，也不修改旧模板默认次数、倍率、已发行卡、价格或套餐。

上线使用通用余额卡前需单独核对发卡策略：默认“同用户同模板累计1次”会阻止同一用户兑换该模板的第二张卡。客户端必须如实提示限制，不能绕过；长期可重复充值的模板参数由运营确认并另行授权设置，不属于本轮代码开发或线上写操作。

## 4. 页面设计

只改现有购买内容区，不改侧栏、全局主题、其他页面和账户入口位置。

1. 套餐卡保留完整权益，周期可选择，主要按钮为“选择套餐/续费”；公开浏览仍匿名、独立加载。
2. 进入同一购买页中的结算视图，展示所选套餐/周期、当前账户、付款方式和订单摘要；窄窗改为纵向布局。
3. 输入兑换码后显示核验结果；只有有效的当前报价和明确确认才可提交。编辑码、切换套餐/周期/账户都会让旧确认失效。
4. 确认区显示标价、个人优惠/折抵、账户余额、兑换码入账/使用金额、剩余余额、最终权益变化。报价加载失败不伪装成0价或0余额。
5. 结果区分别显示购买状态和订阅同步状态，展示订单号、再次查询、必要的重新登录/同步重试。
6. 本页保留“购买记录”“其他礼品卡兑换”和两个微信联系/复制入口；旧兑换查询、确认、历史及订阅同步不删。

匿名目录与登录后的购买资格分离：公开卡片不携带凭据；个人可购/可续费集合、报价和订单不写入公共缓存，不泄露给未登录状态。

## 5. 最小后端扩展候选

以下是设计名称，不是当前已存在或已部署接口；实施时按仓库约定细化。

| 候选接口 | 职责 | 禁止的副作用 |
| --- | --- | --- |
| GET /api/v1/purchase/context | 普通用户自己的余额、币种、可用购买能力及未完成交易提示 | 不修改余额、订单、卡或权益；不暴露管理员字段 |
| POST /api/v1/purchase/quote | 选中套餐/周期与付款材料的资格、真实金额和权益预览；绑定账号、交易意图和有效期 | 不核销卡、不预占余额、不创建业务订单 |
| POST /api/v1/purchase/commit | 校验确认报价与请求键，同事务执行余额型购买并记录可恢复结果 | 不调用第三方支付，不修改旧接口语义 |
| GET /api/v1/purchase/attempts/{request_id} | 仅该账号查询准确结果 | 不通过查询补扣、重兑或创建订单 |

实现约束：

- 报价短期有效（建议5分钟），不是预留库存或冻结卡；提交时仍在同一事务重新校验金额、奖励类型/倍率、资格、余额、权益及并发状态。
- 报价记录评估时点，区分真实业务字段与随执行时间变化的派生字段。时长、起算规则及额度变化需要确认；按实际执行时间生成的到期秒值不能简单与整个旧快照逐字段等值比较。时间推进但金额/资格/权益规则未变时应可提交；若按旧结算规则计算的折抵确实发生最小金额单位变化，则重新报价确认，不默默冻结旧折抵或多扣款。报价有效期是使用上限，不保证期间价格不变。
- 账号、报价和请求键必须绑定；同键不同输入拒绝；已成功请求即使报价过期也应返回原结果，不能再次扣款。
- 一份确认报价只能绑定一个执行身份，数据库约束保护quote与request的关系；不能通过换request_id重复购买同一份报价。不同报价/请求争用同卡、余额或最后套餐名额时也必须保证资源不超额消费，不能只依靠单进程锁。
- 暂未查到请求记录不等于已确定未执行；客户端继续保留待确认状态，只能以原请求键安全恢复，不换键重试。请求键的保留期限和清理策略必须在合同阶段固定，不能删除仍可能恢复的财务结果。
- 增量防重记录表/唯一约束关联请求键、输入摘要、订单和结果。完整卡号、Bearer、密码、订阅凭据不得进入普通日志或持久化结果快照。
- 权益、礼品卡使用记录、买方钱包、邀请人奖励及审计、订单佣金记录/状态、折抵来源订单状态、新订单和成功防重记录必须一起提交或一起回滚；不能用客户端顺序调用模拟这一保证。
- 内部复用/小范围提取原结算与兑换事务逻辑，并用旧路由回归证明没有改变已有语义；不在客户端照抄服务端价格规则。
- type4保留既有发卡快照与独立权益订单语义；是否由新接口包装或继续调用现有幂等兑换，由具体合同决定，不能把0站内收款解释为免费。
- 对旧后端进行能力检测；不支持新合同则保留现有展示/独立兑换功能，明确完整结算暂不可用，不静默降级到不安全扣款。
- 仅新增兼容结构，不删除原表/字段。生产迁移、发布、模板设置均不在本轮开发授权内。

## 6. 完成与验收标准

- Given 未登录，When 浏览并选择套餐，Then 仍可看完整公开套餐，消费操作前登录且保留选择。
- Given 有效报价和足够余额/纯余额码，When 用户确认，Then 一次购买只有一份卡使用/扣款/订单/权益结果；余额差额正确。
- Given 价格、奖励、资格变化或不足，When 提交，Then 不消耗卡、不扣款、不发权益，提示重新确认/补足方式。
- Given 服务端已成功但响应丢失，When 重启客户端查询/重试同请求，Then 找回同一结果，不新增消费。
- Given 另一账号/设备有操作，When 查询或提交，Then 严格按账号和请求隔离，不自动处理无关订单。
- Given 指定套餐码，When 成功兑换，Then 保持原快照及叠加/续期规则，与标准余额订单不混淆。
- Given 购买完成但同步失败，When 用户重试，Then 只同步订阅，不重复付款。
- 浅/深色、320/360px、桌面、2x文字和键盘操作可用；旧购买入口、匿名隔离与其他页面回归不变。
